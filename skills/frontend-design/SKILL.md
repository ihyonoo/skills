## 1. 방향을 먼저 묻는다

고정된 기본 스타일을 두지 않는다. 코드를 쓰기 전에 선택지 형태로 확인한다.

- **참고할 화면** — 마음에 드는 서비스나 사이트가 있는지 먼저 묻는다. 말로 된 설명보다 훨씬 정확하다
- **톤** — 절제된 에디토리얼(여백 넓게, 장식 최소) / 밀도 높은 대시보드(정보 빽빽하게) / 참고 대상을 따름
- **다크모드** — 라이트만 만들지, 둘 다 만들지

스택은 묻기 전에 기존 코드에서 확인한다. 이미 쓰는 것이 있으면 그걸 따르고, 새로 정해야 할 때만 묻는다.

## 2. AI 티를 미리 차단한다

화면을 만들기 전에 `references/ai-tells.md`를 읽는다. 흔한 기본값 그대로 쓰면 티가 나는 지점들이 정리돼 있다.

Tailwind·shadcn/ui 구체 지침은 `references/tailwind.md`.

## 3. 구조가 다른 변형을 2~3개 만든다

**색만 다른 것은 변형이 아니다.** 다음 중 최소 둘이 실제로 달라야 한다.

- 레이아웃 — 배치가 다른가
- 정보 위계 — 무엇을 가장 크게 보여주는가
- 주요 동작 — 핵심 버튼이 어디에 어떤 형태로 있는가

살짝씩 다른 카드 그리드 세 개는 변형이 아니라 벽지다.

**보는 방법** — 한 화면에서 전환할 수 있게 한다. URL 쿼리(`?variant=a`)로 고르고 화면 하단에 전환 바를 띄운다.

**빈 라우트에 만들지 않는다.** 실제 데이터와 실제 주변 UI 안에 넣는다. 빈 페이지는 디자인 문제를 숨긴다.

각 변형이 무엇을 다르게 시도했는지 한 줄씩 설명을 붙인다. 디자인 용어 없이 쓴다.

## 4. 고르고 마감한다

선택된 안만 남기고 나머지 변형과 전환 바를 지운다. 그다음 마감한다.

- 로딩 상태 / 빈 목록 / 에러 상태 — 이 셋이 완성도를 가른다
- 좁은 화면에서 깨지지 않는지
- 키보드만으로 조작되는지, 포커스가 보이는지
- 본문과 배경의 명도 대비

## 하지 않는 것

- 방향 확인 없이 바로 코드 쓰기
- 변형이랍시고 색과 문구만 바꾸기
- 프로토타입 코드를 그대로 프로덕션에 올리기 — 고른 뒤 다시 쓴다
- 화면을 보여주지 않고 "예쁘게 만들었다"고 보고하기
